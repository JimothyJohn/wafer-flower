01
One-time setup

Install the Feature Studio

Custom features live in a Feature Studio — a code tab inside an Onshape document. You install once, version it, and every Part Studio in the document (or any document that links it) gets two new toolbar features.

  1. Open (or create) your Wafer Halo Onshape document.
  2. Click the + at the bottom-left tab bar → Create Feature Studio. Name it halo-beveloid.
  3. Delete the stub content and paste the entire contents of scripts/onshape/wafer_halo_beveloid.fs.
  4. Press ⌘S / Ctrl S — the studio commits (compiles). Green check in the tab = good.
  5. Open any Part Studio → toolbar → the puzzle-piece Custom features flyout → you'll see Halo Beveloid Band and Halo Beveloid Pinion.
First-commit expectations The geometry math in this file is parity-tested against the Python model to 1 × 10⁻⁹ (all 11 spec quantities), but the file has not been executed inside Onshape's runtime. If the studio flags a standard-library call on commit (sketch or loft API spelling), it's a mechanical fix — paste the error back into the repo session and it gets patched. The math is the load-bearing part.
02
Concept

What these features actually build

The halo's drive is a parallel-axis beveloid pair — conical involute gears whose axes are parallel, not intersecting. The ring's teeth sit on a 45° cone with the big end at the wall; each mm of axial travel trades 1 mm of ring radius for 1 mm of pinion radius, so the centre-radius sum is constant across the face and the pinion's axis points straight out of the wall.

This is why Gear Lab can't produce this pair, as brilliant as it is: its bevel gears are spherical involutes for intersecting shafts. A 45° Gear Lab bevel wants its mate's axis to cross the ring's axis at the cone apex — and on the halo, a radial-axis pinion's swept disc spans its full Ø along the wall normal, straight through the drywall behind or the wafer field in front. Gear Lab also has no ring-sector output, no flush-root module retune, and no joint-phase convention. Use Gear Lab for spurs and intersecting-axis bevels; use these two features for the halo drive.

Feature 1

Halo Beveloid Band — the segment's teeth

Model your segment first (the 46 variable expressions + DXF sketches drive everything except the gear). Then run the feature. It builds at the origin in the same frame the printed parts use: wall face on the XY plane, the 40° sector centred on +X, front face at z = face height.

  1. Accept the defaults (they are the shipped Rev B.3 build) → OK. A notice reports the derived numbers — tooth count, flush module, tip radii, and the pinion centre distance C.
  2. Position your segment so its flat bottom is on XY with the sector centred on +X (that's the repo's native frame — the DXF sketches import this way), or Transform the band solid to the segment.
  3. Boolean → Union the band into the segment body. The root circle lands 1 mm inside the band OD, so the union is watertight by construction — teeth rise straight off the band's outer wall, no gap, exactly like the printed part.
Design on the fly Everything re-derives when you drag a parameter. Change N and the sector angle, tooth count, and phase all follow; change the nominal module and the flush retune keeps the root on the band wall. Tick Full ring to generate all 108 teeth for an assembly-level check — spaces land mid-joint at every seam, so N sector instances tile seamlessly.

Mating it. The feature reports C = 325.53 mm at B.3. In an Assembly:

  1. Insert ring and pinion. Add a Revolute mate on each about its own axis — both axes parallel, pointing out of the wall.
  2. Set the axis-to-axis distance to C, with the pinion at 12 o'clock and its big end toward the viewer (the ring's big end faces the wall — the cones complement).
  3. Add a Gear relation between the two revolutes, ratio 9:1, reverse direction (external pair — they counter-rotate). Drag the ring: the pinion spins 9× the other way, exactly like the Drive view on the hub page.
Mesh fidelity The Python model generates the ring as the swept envelope of its cutter (conjugate by construction; the repo's mesh gate measures 0.00000 mm³ interference). These features loft analytic involute sections — identical at the mid-face, a few hundredths off toward the faces. Visually and kinematically indistinguishable in Onshape; for anything you print, the repo's segment_stl.py gates remain the authority.
05
Options

Spiral teeth, one slider

Set Spiral angle on both features (same value, and it must match on both). The wall section rotates by tan(spiral) · face / pitch_r — the same twist the Python twist-extrude applies — so the flanks become ruled helicoids and the pair stays complementary.

The repo ships 0° (straight) deliberately: at 0.3 rpm a spiral buys no smoothness, and its ~tan(sp) axial thrust component would fight the idler-groove mount — the ring's only axial restraint. If you want the spiral look, 35° matches the old aesthetic; just know the groove takes the thrust.

06
Constraints that don't move

The two numbers Onshape can't see

Two halo-level constraints live outside the gear geometry. The features can't enforce them — the Python gates do, on every CI run:

ConstraintValue @ B.3What breaks if violated
gear_F ceiling — the band face must clear the neighbour wafer's clearance plane over the leading ~15–20° of the sector≤ ≈ 4.83 mm
(computed live by gear_F_ceiling())		The mandatory clearance cut planes the leading teeth to partial height and sheds slivers at the disc rim — the exact regression the repo gates against.
Tooth count ≡ 0 (mod N) — enforced by construction here (teeth = tps × N)108 = 12 × 9The pattern breaks at every segment joint; the ring stops tiling.

If you explore a different face height or tilt in Onshape, run python3 scripts/segment_stl.py --gear_F <x> before printing — exit 0 with the gate line means the clearance cut removed zero tooth material.

07
Working together

Collaboration: versions, links, and the repo loop

Onshape's collaboration model is what makes the custom-feature route worth it:

  • Share the document (Share → email or link). Edits are simultaneous and live — two people can have the same Part Studio open; feature regenerations propagate in real time. No files, no checkouts.
  • Version the Feature Studio before you lean on it. Right panel → Versions → create V1. Custom features referenced from other documents bind to a version, so downstream models never shift under you when the studio changes.
  • Publish across documents: in any other document, Custom features flyout → Add custom feature → pick your halo-beveloid document at version V1. Team members can use the features without ever seeing the code.
  • Branch to experiment: Versions panel → branch a workspace (e.g. spiral-35), crank the spiral slider, compare, and merge back if it wins — Onshape's branching is real, like git for CAD.
  • The repo loop: the git repo stays the source of truth for printed parts. Check your Onshape rebuild against the shipped solids by importing stl/step/segment.stp (view-only reference), or export your Part Studio STL into stl/my_frame_segment.stl — viewer_export.py carries it through to the web viewer as a compare overlay (mis-orientation warns, never gates).
  • Update path: when the repo's gear parameters change, this page's crib numbers and the FS defaults are regenerated together — diff scripts/onshape/wafer_halo_beveloid.fs, paste the new version into the Feature Studio, commit, create V2, and re-point consumers when ready.
